이 도구는 공용 Google 계정을 제공하지 않습니다. 본인의 Google Cloud 프로젝트와 OAuth Client를 직접 만들고, 본인의 Google Form과 Gmail을 연결합니다. 처음 한 번만 정확히 설정하면 이후에는 신청자 동기화 → 입금 CSV 대조 → 메일 발송 흐름에 집중할 수 있습니다.

시작 전 준비물

Google Form을 소유하거나 응답을 볼 수 있는 Google 계정, 은행 CSV, 녹화본 URL(예: YouTube 일부공개)

예상 설정 범위

Google Cloud 프로젝트 1개 · Forms API · Gmail API · OAuth Web Client 1개

Google 연결 전에 화면부터 보고 싶다면 · 관리 화면의 설정 → 로컬 데이터 관리 → 샘플 데이터 넣기를 사용하세요. 운영 대시보드에는 샘플 버튼을 두지 않습니다.

전체 흐름

먼저 구조만 이해하면 어렵지 않습니다.

이 사이트는 프로그램 파일만 제공합니다. 신청자와 은행 데이터는 브라우저 IndexedDB에 저장되고, Google API 호출은 사용자가 승인한 짧은 수명의 Access Token으로 브라우저에서 직접 실행합니다.

01
Google Cloud

사용자 본인의 프로젝트·API·OAuth Client를 준비합니다.

02
Google Form

신청 응답을 읽고 질문을 이름·입금자명·이메일 등에 매핑합니다.

03
은행 CSV

브라우저에서 파싱하고 입금자명+금액을 정확 비교합니다.

04
Gmail

입금확인된 사람에게 사용자 Gmail 계정으로 개별 발송합니다.

중요: 이 도구는 브라우저를 닫은 동안 백그라운드에서 Form을 감시하지 않습니다. 관리 화면을 열고 전체 폼 동기화 또는 강의 히스토리의 이 강의 폼 동기화를 실행할 때 연결된 Form 응답을 확인하고 로컬 히스토리에 병합합니다.
현황 숫자는 바로가기입니다. · 대시보드의 기본 순서는 전체 신청 → 입금확인 → 입금대기 → 확인필요 → 발송가능 → 발송완료입니다. 대시보드·입금 관리·강의 히스토리의 숫자 카드를 누르면 해당 상태만 즉시 필터링합니다. 강의 히스토리에서는 페이지를 벗어나지 않고 아래 신청 목록만 바뀝니다.
Google Cloud · BYO OAuth

1. 내 Google Cloud 프로젝트 준비하기

Google Cloud 설정도 사용자가 직접 소유합니다. 이 서비스 운영자가 공용 Client ID나 Client Secret을 제공하지 않습니다.

1

Google Cloud에서 전용 프로젝트를 만듭니다.

Google Cloud Console에서 새 프로젝트를 만들고 알아보기 쉬운 이름을 지정합니다. 예: ClassRelay. 이후 모든 API와 OAuth 설정은 반드시 이 프로젝트가 선택된 상태에서 진행합니다.

Google Cloud 새 프로젝트 열기 ↗

완료 기준 · 상단 프로젝트 선택기에 방금 만든 프로젝트가 표시됩니다.
2

Google Forms API를 사용 설정합니다.

API 및 서비스에서 Google Forms API를 찾아 사용 설정합니다. 이 API가 꺼져 있으면 폼 제목·질문·응답을 가져올 수 없습니다.

Google Forms API 열기 ↗

완료 기준 · 화면에 `사용 설정됨(Enabled)` 상태가 표시됩니다.
3

Gmail API를 사용 설정합니다.

같은 프로젝트에서 Gmail API를 사용 설정합니다. 이 도구는 받은편지함 읽기 권한이 아니라 메일 발송 권한만 요청합니다.

Gmail API 열기 ↗

완료 기준 · Gmail API 역시 `사용 설정됨` 상태입니다.
4

Google Auth Platform의 앱 정보를 설정합니다.

Google Auth Platform에서 앱 이름과 지원 이메일을 입력합니다. 본인 업무용이라면 앱 이름은 `ClassRelay`처럼 구분하기 쉬운 이름이면 충분합니다.

Google Auth Platform 열기 ↗

이 프로젝트를 본인만 사용하는 동안에는 Testing 상태와 본인 계정을 Test user로 등록하는 흐름이 가장 단순합니다. 불특정 다수가 동일 OAuth 프로젝트를 쓰는 구조가 아닙니다.
5

Audience에서 본인 Google 계정을 Test user로 추가합니다.

Audience가 External + Testing이라면 `Test users`에 실제 Google Form과 Gmail을 사용할 본인 계정을 추가합니다. 이 단계가 빠지면 권한창에서 403 access_denied가 발생할 수 있습니다.

완료 기준 · 로그인할 Google 계정이 Test users 목록에 보입니다.
Web client

2. OAuth Web Client 만들기

브라우저에서 Google Identity Services Token Model을 사용하므로 Web application Client ID와 정확한 JavaScript origin이 필요합니다. Client Secret은 이 도구에 입력하지 않습니다.

1

Clients에서 Web application을 만듭니다.

Google Auth Platform의 Clients에서 새 클라이언트를 만들고 유형을 Web application으로 선택합니다. 이름 예: `ClassRelay Web`.

OAuth Clients 열기 ↗

2

Authorized JavaScript origins에 현재 사이트 주소를 넣습니다.

경로를 포함하지 않고 scheme + host + port까지만 입력합니다. 아래 값은 현재 이 페이지의 origin을 자동 표시합니다.

AUTHORIZED JAVASCRIPT ORIGIN · 복사용

로컬에서 테스트한다면 사용하는 포트까지 정확히 추가합니다.

LOCAL TEST EXAMPLE
http://localhost:5173
Redirect URI가 아닙니다. 이 버전은 서버 callback을 사용하는 OAuth Web Server Flow가 아니라 Google Identity Services의 브라우저 Token Model을 사용합니다. 따라서 앱 설정에 필요한 것은 Authorized JavaScript origin입니다.

Google Token Model 공식 문서 ↗

3

Client ID만 복사합니다.

생성 후 표시되는 ...apps.googleusercontent.com 형태의 Client ID를 복사합니다. ClassRelay의 브라우저 Token Model에서는 Client Secret을 사용하거나 입력하지 않습니다.

완료 기준 · Client ID를 복사해 둘 수 있고, Authorized JavaScript origins에 실제 사용 주소가 들어가 있습니다.
4

ClassRelay의 설정에 Client ID를 저장합니다.

관리 화면 → 설정 → Google OAuth의 Client ID 입력란에 붙여넣고 저장합니다. 이 값은 현재 브라우저의 IndexedDB에 저장됩니다.

설정 화면 열기 →

Google Access Token은 백업 파일이나 IndexedDB에 저장하지 않습니다. API 작업 중 토큰이 만료되면 Google 권한창을 다시 열어 새 토큰을 받습니다.
Google Forms

3. 새 강의에 신청 Form 연결하기

ClassRelay에서는 강의가 중심입니다. 새 강의를 만들고 그 강의의 Google Form URL을 한 번 연결하면 이후 신청·입금·발송·CS 히스토리가 같은 강의에 누적됩니다.

1

먼저 강의를 추가합니다.

강의 관리에서 강의명, 가격, 녹화본 URL을 저장합니다. 새 강의를 저장하면 Google Form도 지금 연결할까요? 안내가 나오며 바로 연결을 이어갈 수 있습니다.

다른 진입점 · 대시보드 상단의 폼 추가 또는 강의 관리의 폼 연결에서도 같은 연결 화면을 열 수 있습니다.
2

Google Form의 편집 URL과 연결할 강의를 선택합니다.

주소가 대략 https://docs.google.com/forms/d/FORM_ID/edit 형태인 Form URL을 입력합니다. ClassRelay는 Google Drive 전체 파일 목록 권한을 요청하지 않으므로 계정의 모든 Form을 자동으로 나열하지 않습니다.

폼 추가 → Form URL 입력 → 연결할 강의 선택 → 폼 읽기 순서로 진행합니다.

3

질문 자동 매핑을 확인합니다.

이름, 입금자명, 이메일, 연락처, 결제금액을 질문 제목을 기준으로 추천합니다. 이 구조에서는 Form 자체가 이미 특정 강의에 연결되어 있으므로 강의 질문을 매핑하지 않습니다.

  • 입금자명 질문을 별도로 두는 것을 권장합니다.
  • Google Form 자체 이메일 수집을 켠 경우 폼 자체 수집 이메일을 사용할 수 있습니다.
  • 결제금액 질문이 없거나 값이 비어 있으면 연결된 강의의 등록 가격을 사용합니다.
4

동기화 범위를 구분해서 사용합니다.

대시보드와 상단의 전체 폼 동기화는 사용 중인 강의에 연결된 활성 Form을 모두 확인합니다. 강의 히스토리의 이 강의 폼 동기화는 현재 강의 Form 하나만 확인합니다.

현재 구현은 각 Form의 응답 목록을 확인한 뒤 response ID를 기준으로 기존 로컬 데이터와 병합합니다. 같은 응답을 다시 확인해도 기존 입금확인, 연결 입금, 발송일, 발송횟수, CS 메모는 초기화하지 않습니다.

중요 · 새 Form을 새 강의에 연결해도 과거 강의의 Form·신청·발송 히스토리는 그대로 남습니다.

강의

4. 강의·Form·녹화본을 한 묶음으로 관리하기

각 강의는 자체 Google Form 연결, 녹화본 URL, 메일 템플릿, 신청/입금/발송/CS 히스토리를 가집니다.

1

강의명, 가격, 녹화본 URL을 등록합니다.

ClassRelay는 YouTube API를 사용하지 않습니다. 강의 관리에 사용자가 입력한 녹화본 URL을 메일 템플릿의 {{녹화본URL}}에 넣어 전달합니다.

2

강의 관리에서 Form 연결 상태를 확인합니다.

각 강의 카드에는 Form 연결 여부와 마지막 동기화 시각이 표시됩니다. Form이 없으면 폼 연결, 이미 연결되어 있으면 폼 설정에서 질문 매핑을 확인할 수 있습니다.

3

강의 히스토리를 CS 기준 화면으로 사용합니다.

히스토리에는 해당 강의의 신청 건이 신청번호와 함께 누적됩니다. 신청자 행을 선택하면 같은 화면에서 입금 연결, 최종 발송일, 발송횟수, Gmail 메시지 ID, CS 메모와 발송 당시 내용을 확인할 수 있습니다.

이 강의만 최신 신청을 확인하고 싶다면 상단의 이 강의 폼 동기화를 사용합니다. 최초 발송할 신청자가 있다면 이 강의 발송 대상 n명에서 현재 강의를 그대로 유지한 채 발송 대상 선택 화면으로 이동합니다.

CS 권장 흐름 · 강의 선택 → 고객 검색 → 신청자 행 선택 → 발송이력 확인 → 필요 시 재발송 → CS 메모 저장
4

같은 사람이 다시 신청해도 별도 신청 건으로 보존됩니다.

Google Form response ID가 다르면 동일 이름·이메일·금액이라도 합치지 않습니다. 각 신청 건은 고유 신청번호를 가지며 입금과 발송 상태도 독립적으로 관리됩니다.

동일 이름·금액 후보가 여러 건이면 ClassRelay가 임의로 입금을 붙이지 않고 확인필요 상태로 둡니다.
5

YouTube를 쓴다면 공개 범위를 이해하고 선택합니다.

일부공개(Unlisted) 동영상은 링크를 가진 사람이 시청하고 다시 공유할 수 있으며, 일반적으로 채널 동영상 탭이나 검색 결과에는 표시되지 않습니다. 링크를 받은 사람이 Google 계정 없이도 볼 수 있습니다.

비공개(Private) 동영상은 YouTube에서 허용한 사용자만 볼 수 있어 단순 URL 발송만으로는 접근 권한이 생기지 않습니다. 따라서 ClassRelay의 현재 URL 전달 방식에서는 일부공개 링크가 사용하기 편하지만, 링크 재공유를 막는 접근통제 수단은 아닙니다.

ClassRelay는 YouTube의 시청 권한을 제어하거나 링크 재공유를 차단하지 않습니다.

은행 CSV

5. 은행 입금내역 가져오고 입금 대조하기

CSV 파일은 서버로 전송하지 않고 브라우저에서 읽습니다. 신규 입금내역만 누적 저장하고 가져오기가 끝나면 즉시 자동 매칭합니다.

1

은행에서 CSV 입금내역을 내려받습니다.

스크린샷이나 PDF보다 CSV를 권장합니다. 입금일시, 입금자명(또는 적요), 입금액을 확인할 수 있어야 합니다.

2

입금 관리 → CSV 가져오기를 누릅니다.

열 이름을 자동 인식한 뒤 입금일시, 입금자명, 입금액, 선택 가능한 은행 고유번호/참조번호 매핑을 보여줍니다. 은행마다 열 이름이 다르므로 첫 파일에서는 반드시 확인하세요.

완료 기준 · 입금내역 목록에 이름과 금액이 정상적으로 표시됩니다.
3

CSV를 가져오면 자동 매칭이 즉시 실행됩니다.

정규화 입금자명 100% 일치 + 금액 100% 일치 + 입금일 조건 통과 + 양쪽 후보 1:1일 때만 자동확인합니다. 기본 입금일 조건은 신청 전 1일 ~ 신청 후 7일이며 설정에서 전/후 허용일을 변경할 수 있습니다.

예: `김민수 39,000원` 신청자가 2명인데 `김민수 39,000원` 입금이 1건이면 누구에게도 임의 매칭하지 않고 `확인필요`로 둡니다.
4

이름 오기입은 `유사 후보`로만 제안됩니다.

예를 들어 `김민지` 신청과 `김민정` 입금처럼 이름이 비슷하고 금액·날짜 조건이 맞으면 자동확정하지 않고 신청자 상세에 입금 후보를 표시합니다. 실제 동일인임을 확인한 뒤 `이 입금 연결`을 눌러 수동 연결합니다.

5

나중에 CSV를 또 올려도 기존 기록은 유지됩니다.

이전 입금내역, 기존 매칭, 발송 이력을 삭제하지 않고 CSV에서 새로 발견된 입금내역만 추가합니다. 겹치는 기간의 CSV를 다시 받아 올려도 정규화된 입금일시 fingerprint를 기준으로 중복 삽입을 줄입니다. 은행 고유번호/참조번호가 제공되면 그 값을 중복 판정에 우선 사용합니다.

Gmail

6. 녹화본 메일 보내기

한 번의 BCC 대량메일이 아니라 신청자별 개별메일을 순서대로 보냅니다. 누가 언제 어떤 링크를 받았는지 로컬 로그에 기록됩니다.

1

새 템플릿은 빈 화면에서 직접 작성합니다.

`+ 템플릿 추가`를 누르면 템플릿 이름, 사용 강의, 제목, 본문을 한 번에 입력합니다. 기존 기본 문구가 자동 복사되지 않습니다. 기존 템플릿 내용을 바탕으로 만들고 싶다면 해당 템플릿의 복제를 사용하세요.

사용 가능한 변수는 {{이름}}, {{강의명}}, {{녹화본URL}}, {{신청번호}}, {{금액}}입니다.

2

필요하면 생성하면서 강의별 전용 템플릿을 연결합니다.

새 템플릿의 `사용 강의`는 강의 리스트에서 행을 눌러 선택합니다. 기본 템플릿은 별도 선택 없이 전용 템플릿이 없는 강의에 자동 적용됩니다. 일반 템플릿에서 이미 다른 전용 템플릿이 연결된 강의를 고르면 기존 템플릿 → 새 템플릿 변경 내용을 확인한 뒤에만 교체합니다.

권장 · 대부분의 강의는 기본 템플릿을 쓰고, 안내 문구가 특별한 강의만 전용 템플릿을 연결하면 관리가 단순합니다.
3

생성 직후 새 템플릿이 선택됩니다.

`템플릿 생성`을 누르면 새 템플릿이 저장되고 메일 화면에서 자동 선택됩니다. 이후 미리보기나 추가 편집을 바로 이어갈 수 있습니다. `복제`는 기존 제목·본문을 복사하는 전용 기능으로 유지됩니다.

4

먼저 발송할 강의를 확정합니다.

메일 / 발송로그의 발송 대상 선택을 누르면 강의별 `발송 가능 n명`이 먼저 표시됩니다. 한 번의 발송 작업에는 한 강의만 포함합니다. 강의 히스토리에서 시작하는 경우에는 현재 강의가 이미 확정되어 있으므로 이 강의 발송 대상 n명을 눌러 바로 다음 단계로 이동합니다.

원칙 · 강의는 발송 화면에서 다시 고르는 필터가 아니라 이미 확정된 작업 컨텍스트입니다.
5

그 강의의 발송 가능한 신청 건만 선택합니다.

입금확인, 이메일 형식 정상, 강의 URL 존재, 메일 템플릿 존재, 아직 최초 발송하지 않음, 발송 결과 확인 필요 상태가 아님 등의 조건을 모두 통과한 신청 건만 목록에 표시됩니다. 같은 사람이 여러 강의를 신청했더라도 각 강의 신청 건은 별도의 발송 작업으로 처리합니다.

6

강의와 실제 발송 내용을 마지막으로 확인합니다.

Gmail 호출 전에 확인창에서 강의명, 선택 인원, 사용할 메일 템플릿, 녹화본 URL, 제목 템플릿을 보여줍니다. 서로 다른 강의의 신청 건을 한 발송 작업에 섞을 수 없습니다.

7

처음 발송할 때 Gmail 권한을 승인합니다.

이 도구가 요청하는 Gmail scope는 메일 보내기용 gmail.send입니다. 받은편지함을 읽는 기능은 구현하지 않습니다.

발송에 성공하면 당시 실제 제목·본문·녹화본 URL·수신 이메일·템플릿 이름을 발송 당시 내용으로 저장합니다. 나중에 템플릿을 바꿔도 과거 발송 내용은 바뀌지 않습니다.

Gmail API 권한 공식 문서 ↗

8

`발송 확인 필요`는 자동 재발송하지 않습니다.

네트워크 timeout이나 Gmail 5xx처럼 Gmail이 메일을 실제로 처리했는지 브라우저가 확정할 수 없는 경우 ClassRelay는 발송 확인 필요로 기록합니다. 이 상태에서는 자동으로 다시 보내지 않습니다.

고객이 실제로 받지 못했는지 확인한 뒤 `확인 후 재발송`을 사용하세요. 이전 요청이 Gmail에서 처리되었을 가능성이 있어 중복 발송 경고가 표시됩니다.
9

CS에서는 당시 발송 내용을 직접 확인합니다.

메일 / 발송로그의 전체 폭 발송 내역 테이블 또는 신청자·강의 히스토리 활동 로그에서 `발송 내용 보기`를 누르면 당시 제목·본문·URL을 확인할 수 있습니다. 재발송은 해당 신청 건의 강의를 기준으로 현재 템플릿을 사용합니다.

로컬 데이터

7. 브라우저 데이터 백업하기

중앙 DB가 없다는 것은 운영자가 데이터 소유권을 갖는다는 뜻이지만, 브라우저 데이터를 직접 지우면 앱에서도 사라집니다. 백업은 선택이 아니라 운영 절차로 보는 편이 좋습니다.

1

설정 → 백업 내보내기를 주기적으로 실행합니다.

강의, 신청자, 입금내역, 메일 템플릿, 발송 당시 내용, Form 연결, 설정을 하나의 JSON 파일로 저장합니다. 백업 파일에는 개인정보와 입금내역이 포함될 수 있으므로 본인만 접근할 수 있는 위치에 보관합니다.

2

다른 PC에서는 백업 불러오기로 이동합니다.

새 브라우저에서 사이트를 연 뒤 백업 JSON을 불러오고 Google Client ID 및 권한 상태를 확인합니다. Google Access Token은 백업하지 않으므로 Google 권한은 다시 받을 수 있습니다.

3

브라우저 저장소 유지 요청을 켤 수 있습니다.

지원하는 브라우저에서는 persistent storage를 요청할 수 있습니다. 다만 사용자가 직접 사이트 데이터 삭제를 선택하면 삭제될 수 있으므로 백업을 대체하지는 않습니다.

문제 해결

자주 막히는 지점

설정 문제가 생기면 아래 항목부터 확인하면 대부분 원인을 빠르게 찾을 수 있습니다.

`origin_mismatch` 또는 OAuth Client 관련 오류가 납니다.

Google Cloud의 OAuth Web Client가 맞는지 확인하고 Authorized JavaScript origins에 현재 사이트의 origin이 정확히 들어있는지 확인합니다. `https://도메인/guide`처럼 경로를 넣지 말고 `https://도메인`까지만 넣습니다. 로컬 테스트는 포트까지 일치해야 합니다.

Google 권한창에서 `403 access_denied`가 납니다.

OAuth Audience가 Testing 상태라면 현재 로그인할 계정을 Test users에 추가했는지 확인합니다. 다른 Google 계정으로 승인하고 있지 않은지도 확인합니다.

Form 연결에서 API가 비활성화됐다는 오류가 납니다.

OAuth Client를 만든 Google Cloud 프로젝트와 Google Forms API를 활성화한 프로젝트가 같은지 확인합니다. Google Forms API가 Enabled 상태여야 합니다.

Form을 찾을 수 없거나 권한이 없다고 나옵니다.

공개 `viewform` 링크 대신 편집 URL(`/forms/d/.../edit`)을 사용하고, Google 권한창에서 선택한 계정이 그 Form의 응답을 읽을 수 있는 계정인지 확인합니다.

`전체 폼 동기화`와 `이 강의 폼 동기화`의 차이는 무엇인가요?

전체 폼 동기화는 사용 중인 강의에 연결된 활성 Form을 모두 확인합니다. 이 강의 폼 동기화는 현재 강의에 연결된 Form 하나만 확인합니다. 둘 다 기존 신청·입금·발송·CS 기록을 초기화하지 않고 response ID를 기준으로 병합합니다.

질문 매핑이 틀렸습니다.

자동 추천은 질문 제목의 일반적인 표현을 기준으로 합니다. 해당 Form의 설정에서 이름·입금자명·이메일·연락처·금액을 직접 지정하고 연결 설정을 저장하세요. 강의는 Form 질문이 아니라 Form에 연결한 강의로 고정됩니다.

CSV에서 금액이나 이름이 이상합니다.

은행마다 CSV 열 이름과 인코딩이 다릅니다. 가져오기 화면에서 입금자명·입금액 열을 직접 지정합니다. 그래도 문제가 남으면 실제 은행 CSV 샘플을 개인정보 제거 후 개발 버전에 맞춰 열 해석 규칙을 추가해야 합니다.

같은 사람이 같은 강의를 두 번 신청했습니다.

정상 동작입니다. 서로 다른 Form 응답은 각각 별도 신청 건으로 유지됩니다. 강의 히스토리에서 동일 고객 신청 건을 전환해 각각의 입금·발송 기록을 확인하세요. 같은 이름과 금액 때문에 자동 매칭이 애매해지면 `확인필요`로 남습니다.

고객이 예전에 녹화본을 못 받았다고 합니다.

강의 관리 → 해당 강의 → 히스토리에서 이름이나 이메일을 검색하고 해당 신청자 행을 선택하세요. 최종 발송일, 발송횟수, Gmail 메시지 ID와 활동 로그를 확인한 뒤 같은 화면에서 재발송할 수 있습니다.

과거에 어떤 메일 내용을 보냈는지 확인하고 싶습니다.

신청자 또는 강의 히스토리의 발송 활동에서 `발송 내용 보기`를 누르세요. 성공 발송 당시 제목·본문·녹화본 URL이 발송 당시 내용으로 저장됩니다.

Gmail 발송 중 다시 권한창이 열립니다.

브라우저 Token Model의 Access Token은 짧은 수명으로 발급되며 이 앱은 토큰을 영구 저장하지 않습니다. 만료 후 Google API 작업을 다시 시작할 때 새 토큰을 요청하는 것은 정상 흐름입니다.

브라우저를 바꾸니 신청자 목록이 비었습니다.

운영 데이터는 브라우저별 IndexedDB에 저장됩니다. 기존 브라우저에서 백업 JSON을 내보낸 뒤 새 브라우저에서 복원해야 합니다.
