이 도구는 공용 Google 계정을 제공하지 않습니다. 본인의 Google Cloud 프로젝트와 OAuth Client를 직접 만들고, 본인의 Google Form과 Gmail을 연결합니다. 처음 한 번만 정확히 설정하면 이후에는 신청자 동기화 → 입금 CSV 대조 → 메일 발송 흐름에 집중할 수 있습니다.

OVERVIEW

먼저 구조만 이해하면 어렵지 않습니다.

이 사이트는 프로그램 파일만 제공합니다. 신청자와 은행 데이터는 브라우저 IndexedDB에 저장되고, Google API 호출은 사용자가 승인한 짧은 수명의 Access Token으로 브라우저에서 직접 실행합니다.

01
Google Cloud

사용자 본인의 프로젝트·API·OAuth Client를 준비합니다.

02
Google Form

신청 응답을 읽고 질문을 이름·입금자명·이메일 등에 매핑합니다.

03
은행 CSV

브라우저에서 파싱하고 입금자명+금액을 정확 비교합니다.

04
Gmail

입금확인된 사람에게 사용자 Gmail 계정으로 개별 발송합니다.

중요: 이 도구는 브라우저를 닫은 동안 백그라운드에서 Form을 감시하지 않습니다. 관리 화면을 열고 폼 동기화를 실행할 때 신규 응답을 가져옵니다.
GOOGLE CLOUD · BYO OAUTH

1. 내 Google Cloud 프로젝트 준비하기

Google Cloud 설정도 사용자가 직접 소유합니다. 이 서비스 운영자가 공용 Client ID나 Client Secret을 제공하지 않습니다.

1

Google Cloud에서 전용 프로젝트를 만듭니다.

Google Cloud Console에서 새 프로젝트를 만들고 알아보기 쉬운 이름을 지정합니다. 예: ClassRelay. 이후 모든 API와 OAuth 설정은 반드시 이 프로젝트가 선택된 상태에서 진행합니다.

Google Cloud 새 프로젝트 열기 ↗

완료 기준 · 상단 프로젝트 선택기에 방금 만든 프로젝트가 표시됩니다.
2

Google Forms API를 사용 설정합니다.

API 및 서비스에서 Google Forms API를 찾아 사용 설정합니다. 이 API가 꺼져 있으면 폼 제목·질문·응답을 가져올 수 없습니다.

Google Forms API 열기 ↗

완료 기준 · 화면에 `사용 설정됨(Enabled)` 상태가 표시됩니다.
3

Gmail API를 사용 설정합니다.

같은 프로젝트에서 Gmail API를 사용 설정합니다. 이 도구는 받은편지함 읽기 권한이 아니라 메일 발송 권한만 요청합니다.

Gmail API 열기 ↗

완료 기준 · Gmail API 역시 `사용 설정됨` 상태입니다.
4

Google Auth Platform의 앱 정보를 설정합니다.

Google Auth Platform에서 앱 이름과 지원 이메일을 입력합니다. 본인 업무용이라면 앱 이름은 `ClassRelay`처럼 구분하기 쉬운 이름이면 충분합니다.

Google Auth Platform 열기 ↗

이 프로젝트를 본인만 사용하는 동안에는 Testing 상태와 본인 계정을 Test user로 등록하는 흐름이 가장 단순합니다. 불특정 다수가 동일 OAuth 프로젝트를 쓰는 구조가 아닙니다.
5

Audience에서 본인 Google 계정을 Test user로 추가합니다.

Audience가 External + Testing이라면 `Test users`에 실제 Google Form과 Gmail을 사용할 본인 계정을 추가합니다. 이 단계가 빠지면 권한창에서 403 access_denied가 발생할 수 있습니다.

완료 기준 · 로그인할 Google 계정이 Test users 목록에 보입니다.
WEB CLIENT

2. OAuth Web Client 만들기

브라우저에서 Google Identity Services Token Model을 사용하므로 Web application Client ID와 정확한 JavaScript origin이 필요합니다. Client Secret은 이 도구에 입력하지 않습니다.

1

Clients에서 Web application을 만듭니다.

Google Auth Platform의 Clients에서 새 클라이언트를 만들고 유형을 Web application으로 선택합니다. 이름 예: `ClassRelay Web`.

OAuth Clients 열기 ↗

2

Authorized JavaScript origins에 현재 사이트 주소를 넣습니다.

경로를 포함하지 않고 scheme + host + port까지만 입력합니다. 아래 값은 현재 이 페이지의 origin을 자동 표시합니다.

AUTHORIZED JAVASCRIPT ORIGIN · 복사용

로컬에서 테스트한다면 사용하는 포트까지 정확히 추가합니다.

LOCAL TEST EXAMPLE
http://localhost:5173
Redirect URI가 아닙니다. 이 버전은 서버 callback을 사용하는 OAuth Web Server Flow가 아니라 Google Identity Services의 브라우저 Token Model을 사용합니다. 따라서 앱 설정에 필요한 것은 Authorized JavaScript origin입니다.
3

Client ID만 복사합니다.

생성 후 표시되는 ...apps.googleusercontent.com 형태의 Client ID를 복사합니다. Client Secret은 서버 측 작업용 값이며 이 도구에는 넣지 않습니다.

완료 기준 · Client ID를 복사해 둘 수 있고, Authorized JavaScript origins에 실제 사용 주소가 들어가 있습니다.
4

ClassRelay의 설정에 Client ID를 저장합니다.

관리 화면 → 설정 → Google OAuth의 Client ID 입력란에 붙여넣고 저장합니다. 이 값은 현재 브라우저의 IndexedDB에 저장됩니다.

설정 화면 열기 →

Google Access Token은 백업 파일이나 IndexedDB에 저장하지 않습니다. API 작업 중 토큰이 만료되면 Google 권한창을 다시 열어 새 토큰을 받습니다.
GOOGLE FORMS

3. 신청 Form 연결하기

Form 자체를 DB로 쓰는 것이 아니라, 신규 응답을 브라우저의 로컬 DB에 동기화하는 구조입니다.

1

Google Form의 편집 URL을 복사합니다.

주소가 대략 https://docs.google.com/forms/d/FORM_ID/edit 형태인 편집 화면 URL을 사용합니다. 공개 응답용 `viewform` 주소가 아니라 본인이 편집할 수 있는 Form 주소를 권장합니다.

2

설정에서 Form URL을 입력하고 `폼 읽기`를 누릅니다.

처음 실행하면 Google 계정 선택과 권한 동의 창이 열립니다. Forms 본문 읽기와 응답 읽기 권한만 요청합니다.

완료 기준 · Form 제목, Form ID, 질문 개수가 설정 화면에 표시됩니다.
3

질문 자동 매핑을 반드시 확인합니다.

이름, 입금자명, 이메일, 연락처, 강의, 결제금액을 질문 제목을 기준으로 자동 추천합니다. 질문 제목이 독특하거나 표현이 다르면 드롭다운으로 직접 선택하세요.

  • 입금자명 항목이 없다면 신청자 이름을 fallback으로 사용하지만, 실제 운영에서는 별도 질문을 두는 편이 좋습니다.
  • Google Form 자체 이메일 수집을 켠 경우 `폼 자체 수집 이메일`을 선택할 수 있습니다.
  • 결제금액 질문이 없어도 강의 관리에 동일 강의명과 가격이 등록되어 있으면 동기화할 때 가격을 보완합니다.
4

`기존 응답 동기화`를 실행합니다.

FormResponse ID를 신청자 ID로 사용하므로 같은 응답을 반복 동기화해도 중복 생성되지 않습니다. 이후에는 상단의 `폼 동기화` 버튼으로 신규 응답만 가져옵니다.

COURSES

4. 강의와 녹화본 URL 등록하기

신청자의 `강의` 값과 강의 관리의 `강의명`을 연결합니다. 메일을 보낼 때 YouTube URL은 강의 관리에서 가져옵니다.

1

강의 관리에서 강의를 추가합니다.

강의명, 가격, YouTube 녹화본 URL을 입력합니다. Form의 강의 선택지와 강의명을 동일하게 유지하면 가장 안정적입니다.

2

YouTube 공유 범위를 확인합니다.

일부공개(Unlisted) 링크는 링크를 아는 사람이 다시 공유할 수 있습니다. 이 도구는 URL 전달 자동화를 담당하며 YouTube 링크 재공유 자체를 기술적으로 차단하지는 않습니다.

BANK CSV

5. 은행 거래내역 가져오고 입금 대조하기

CSV 파일은 서버로 전송하지 않고 브라우저에서 읽습니다. 파일을 가져온 다음 정확 일치만 자동 매칭합니다.

1

은행에서 CSV 거래내역을 내려받습니다.

스크린샷이나 PDF보다 CSV를 권장합니다. 거래일시, 입금자명(또는 적요), 입금액을 확인할 수 있어야 합니다.

2

입금 관리 → CSV 가져오기를 누릅니다.

열 이름을 자동 인식한 뒤 거래일시, 입금자명, 입금액 매핑을 보여줍니다. 은행마다 열 이름이 다르므로 첫 파일에서는 반드시 확인하세요.

완료 기준 · 입금내역 목록에 이름과 금액이 정상적으로 표시됩니다.
3

자동 매칭을 실행합니다.

신청자와 거래가 입금자명 + 금액으로 정확히 일치하고 양쪽 후보가 각각 하나일 때만 자동확인합니다.

예: `김민수 39,000원` 신청자가 2명인데 `김민수 39,000원` 입금이 1건이면 누구에게도 임의 매칭하지 않고 `확인필요`로 둡니다.
4

이름 오기입 등은 신청자 상세에서 수동 확인합니다.

실제 동일인임을 사람이 확인한 경우에만 `수동 입금확인`을 사용합니다. 이 기록은 활동 로그에 남습니다.

GMAIL

6. 녹화본 메일 보내기

한 번의 BCC 대량메일이 아니라 신청자별 개별메일을 순서대로 보냅니다. 누가 언제 어떤 링크를 받았는지 로컬 로그에 기록됩니다.

1

메일 템플릿을 확인합니다.

메일 / 발송로그에서 제목과 본문을 수정할 수 있습니다. {{이름}}, {{강의명}}, {{녹화본URL}} 변수를 사용할 수 있습니다.

2

신청자에서 발송 대상을 선택합니다.

입금확인, 이메일 형식 정상, 강의 URL 존재, 아직 최초 발송하지 않은 신청자만 일반 발송 대상이 됩니다.

3

처음 발송할 때 Gmail 권한을 승인합니다.

이 도구가 요청하는 Gmail scope는 메일 보내기용 gmail.send입니다. 받은편지함을 읽는 기능은 구현하지 않습니다.

4

재발송은 신청자 상세에서 명시적으로 실행합니다.

이미 발송완료 상태인 사람은 일반 선택발송에서 제외됩니다. 고객이 메일을 잃어버렸을 때만 `재발송`을 사용합니다.

LOCAL DATA

7. 브라우저 데이터 백업하기

중앙 DB가 없다는 것은 운영자가 데이터 소유권을 갖는다는 뜻이지만, 브라우저 데이터를 직접 지우면 앱에서도 사라집니다. 백업은 선택이 아니라 운영 절차로 보는 편이 좋습니다.

1

설정 → 백업 내보내기를 주기적으로 실행합니다.

강의, 신청자, 입금내역, 발송로그, 설정을 하나의 JSON 파일로 저장합니다. 백업 파일에는 개인정보와 거래내역이 포함될 수 있으므로 본인만 접근할 수 있는 위치에 보관합니다.

2

다른 PC에서는 백업 불러오기로 이동합니다.

새 브라우저에서 사이트를 연 뒤 백업 JSON을 불러오고 Google Client ID 및 권한 상태를 확인합니다. Google Access Token은 백업하지 않으므로 Google 권한은 다시 받을 수 있습니다.

3

브라우저 저장소 유지 요청을 켤 수 있습니다.

지원하는 브라우저에서는 persistent storage를 요청할 수 있습니다. 다만 사용자가 직접 사이트 데이터 삭제를 선택하면 삭제될 수 있으므로 백업을 대체하지는 않습니다.

TROUBLESHOOTING

자주 막히는 지점

설정 문제가 생기면 아래 항목부터 확인하면 대부분 원인을 빠르게 찾을 수 있습니다.

`origin_mismatch` 또는 OAuth Client 관련 오류가 납니다.

Google Cloud의 OAuth Web Client가 맞는지 확인하고 Authorized JavaScript origins에 현재 사이트의 origin이 정확히 들어있는지 확인합니다. `https://도메인/guide`처럼 경로를 넣지 말고 `https://도메인`까지만 넣습니다. 로컬 테스트는 포트까지 일치해야 합니다.

Google 권한창에서 `403 access_denied`가 납니다.

OAuth Audience가 Testing 상태라면 현재 로그인할 계정을 Test users에 추가했는지 확인합니다. 다른 Google 계정으로 승인하고 있지 않은지도 확인합니다.

Form 연결에서 API가 비활성화됐다는 오류가 납니다.

OAuth Client를 만든 Google Cloud 프로젝트와 Google Forms API를 활성화한 프로젝트가 같은지 확인합니다. Google Forms API가 Enabled 상태여야 합니다.

Form을 찾을 수 없거나 권한이 없다고 나옵니다.

공개 `viewform` 링크 대신 편집 URL(`/forms/d/.../edit`)을 사용하고, Google 권한창에서 선택한 계정이 그 Form의 응답을 읽을 수 있는 계정인지 확인합니다.

질문 매핑이 틀렸습니다.

자동 추천은 질문 제목의 일반적인 표현을 기준으로 합니다. 설정의 드롭다운에서 이름·입금자명·이메일·강의·금액을 직접 지정하고 `매핑 저장`을 누르세요.

CSV에서 금액이나 이름이 이상합니다.

은행마다 CSV 열 이름과 인코딩이 다릅니다. 가져오기 화면에서 입금자명·입금액 열을 직접 지정합니다. 그래도 문제가 남으면 실제 은행 CSV 샘플을 개인정보 제거 후 개발 버전에 맞춰 열 해석 규칙을 추가해야 합니다.

Gmail 발송 중 다시 권한창이 열립니다.

브라우저 Token Model의 Access Token은 짧은 수명으로 발급되며 이 앱은 토큰을 영구 저장하지 않습니다. 만료 후 Google API 작업을 다시 시작할 때 새 토큰을 요청하는 것은 정상 흐름입니다.

브라우저를 바꾸니 신청자 목록이 비었습니다.

운영 데이터는 브라우저별 IndexedDB에 저장됩니다. 기존 브라우저에서 백업 JSON을 내보낸 뒤 새 브라우저에서 복원해야 합니다.
